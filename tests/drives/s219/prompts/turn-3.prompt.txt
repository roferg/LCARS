# MBR builder — mock rendering

## The problem
The DX Scorecard already ships an MBR (Monthly Business Review) builder, but the
captain wants to *see the experience* end to end — and several of its surfaces
(carried-over badge, empty state, lock/unlock/discard) currently render with
browser defaults. This mock shows the whole flow so the look can be judged.

## Decisions
- **T1 — Build to the real DX Scorecard tokens in both themes.** The basis shows
  the project ships dark ("night", the `:root` default) *and* a bespoke cool-blue
  light ("day") theme; the mock renders in both via `data-color-mode` because the
  captain asked to see "the experience," and light is the non-obvious one to get
  right.
- **T1 — Reuse existing shapes rather than invent chrome.** `.bucket-card` with a
  4px `--c` accent, the KPI grid with an Insight column, the five status
  silhouettes, `.icon-btn`/`.btn` families and tabular-num 680-weight values are
  all lifted from `src/styles.css`, so this reads as the same product.
- **T1 — The Insight column is the point of the builder.** Each KPI's value/target
  is already collected; the human act being designed is writing one insight per
  KPI and then locking the month, so the layout centres the insight textarea and
  tracks "insights added" as the completion metric.
- **T1 — Locking is per-bucket, publishing is the whole month.** Locked buckets
  render read-only with a Lock badge and an Unlock control; the top-level "Lock
  month" is the publish action. This gives the captain a reason for both an
  unlock modal and a lock modal.
- **T2 — A month starts with a data pull, not a blank form.** The captain asked
  how you get started; the entry point is a Reviews list where the next month
  sits unstarted until you "Pull data & start", which fetches values/targets/
  deltas per bucket (shown as a collection progress screen) and then drops you
  into the builder. Insights are the only thing you author; everything numeric
  arrives from the pull.
- **T2 — A KPI's insight is "filled" when the textarea is non-empty.** The mock
  treats any text in the insight box as a completed insight and counts it toward
  the "insights added" progress; there is no separate save/confirm step per KPI.
  (Whether text-presence alone should equal "complete", or status must also be
  set, remains an open question below.)
- **T7 — Multi-value KPIs list every value, like the default view.** A KPI with
  several data fields renders all of them as a label/value cohort breakdown (the
  default view's `cohort-list`) — no collapsing, no expander, and no single
  averaged or median headline. The reviewer sees each source's real number
  (gh/gh, Mode, Copilot, Go SDLC) directly in the value column.
- **T8 — Each value in a multi-value KPI shows its own change since the last MBR.**
  Every source row carries its own delta versus the last published MBR (coloured by
  whether the move is good or bad, with a "no change" state), so a multi-value KPI
  gives per-source trend rather than one number for the whole metric.
- **T3 — Values are editable in place when there's no automated source.** Auto and
  manual KPIs are tagged; manual values render as an editable input (like today's
  default scorecard view) rather than static text, and the data pull marks such
  KPIs "Enter manually" instead of failing. Settled because some values are pulled
  by hand and the builder must let the user type them, not block on a source.
- **T4 — Manual values are seeded from the default view's latest, then editable.**
  A metric with no automated source is prefilled from its most recent value on the
  default scorecard tab and tagged "From default view · edit to override," so the
  user starts from a real number rather than a blank field but can still correct
  metrics that can't be gathered automatically.
- **T5 — The automatic-collection UI matches the shipping Update KPIs page.** Each
  auto KPI has its own control cycling **Collect → Collecting… → ✓ Updated** (then
  **Re-collect**), with **Try again** on failure and a "was <old> · as of <date>"
  treatment on the refreshed value. One toolbar **Update all automatically** sweeps
  every automatable KPI in order behind an indeterminate progress strip, preceded
  by a warning line stating it only collects the automated ones (N of M) and leaves
  manual KPIs unchanged. Settled by reusing the pattern users already know rather
  than inventing new refresh affordances; collection acts per-KPI and all-at-once,
  not per-bucket.
- **T4 — Every comparison is against the last published MBR.** Deltas read "vs last
  MBR," not against an arbitrary previous month, so the review always compares to
  the last thing that was actually published.
- **T6 — Off track is an X, on track is a filled circle.** The off-track marker was
  made a distinct X shape so it is told apart from the on-track circle by shape
  alone — the two must not rely on red/green, which colourblind readers can't
  separate. The other three markers (triangle Watch, ring Tracking, half-circle
  WIP) are unchanged.
- **T6 — "Update all automatically" lives inside its warning box.** The bulk-collect
  action sits in the same amber box as the caveat that governs it (only automatable
  KPIs, N of M, manual ones untouched), so the button and the rule it obeys are
  read together rather than the action floating in the toolbar.
- **T6 — There is no separate "empty bucket" state.** Because every KPI's value is
  collected on the pull, a not-yet-started bucket is not blank: it shows its KPI
  rows with values and status and empty insight boxes, and the bucket header counts
  "N of M insights." Completeness is per-KPI insight coverage, never a whole-bucket
  blank screen — a bucket can't be in a state where its collected values are hidden
  behind a "start" prompt.

# DX Scorecard — repo context

Declarative facts about this repository, for anyone (human or agent) working in
it. Read this before deriving anything about the layout. Keep it current: if a
statement here stops being true, fix the statement in the same change.

## What this is

A static-first **Developer Experience (DX) Scorecard**: a React + TypeScript +
Vite app using GitHub Primer, rendering KPI data from checked-in JSON. It builds
to `dist/` and deploys to GitHub Pages. There is **no backend** — everything the
deployed site shows comes from JSON committed to the repo.

## The one rule people get wrong

**`docs/mocks/` is a design REFERENCE. It is never the thing you change, and it
is never shipped.**

- It holds standalone, dependency-free HTML/CSS/JS mocks (`index.html`,
  `update-kpis.html`, their `.css`/`.js`, plus `styles.css` design tokens and
  `data.js` fake data). Open them in a browser directly — no build.
- **Never edit anything under `docs/mocks/` to implement a feature.** A change
  there ships nothing: GitHub Pages publishes `dist/`, built by `npm run build`
  from `src/`. Editing the mock produces a green build and zero user-visible
  change. This has actually happened.
- When a mission says "match the mock", the work is to **PORT** the mock's CSS
  rules and class vocabulary into `src/styles.css` and the React components —
  reusing the mock's class names (`.krow`, `.tag-auto`, `.state-chip`, …) so its
  rules actually apply. Do **not** invent a parallel vocabulary and re-derive the
  visual values by eye; that produces something that behaves right and looks
  wrong. This has also actually happened.
- The mock is authoritative for **look and interaction**, never for data shape or
  contracts — those live in `shared/types.ts`.

## Data model (`shared/types.ts` is the source of truth)

Nested `Snapshot → Bucket[] → Kpi[]`. Exported types: `MetricStatus`,
`SubReading`, `MetricValue`, `Kpi`, `Bucket`, `Reading`, `Amendment`,
`Snapshot`, `ConfigKpi`, `ConfigBucket`, `ScorecardConfig`.

- `data/config.json` is the **roster only** — bucket/KPI identity, targets,
  `aiUpdateInstructions`, `drilldown`. No values, no statuses.
- `data/snapshots/<id>.json` are **immutable, self-contained** point-in-time
  snapshots carrying their own roster *and* readings. Ids are date-keyed
  `YYYY-MM-DD.N`. A snapshot is `draft` until explicitly locked.
- A KPI is **automatable iff its `aiUpdateInstructions` is non-empty.** That
  field is the single canonical signal — there is no separate `autoUpdate` field,
  and adding one has been explicitly rejected.

## Dev-only surfaces (and why they must stay that way)

Editing exists **only** under `vite dev`. The production bundle must contain no
editing UI and no endpoints.

- Gate every editing surface behind `import.meta.env.DEV` so Rollup tree-shakes
  it out. `src/build-purity.test.ts` runs a real production build and asserts the
  emitted assets contain no editing markers — it will fail if you leak one.
- The local bridge is a Vite plugin, `scripts/dev-write-plugin.ts`
  (`configureServer`, `apply: 'serve'`), exposing:
  `PUT /__data/config` · `PUT /__data/snapshots/:id` · `POST /__mbr/refresh` ·
  `POST /__collect/<kpiId>`.
  **It already exists — extend it, never create a second one.** New endpoints
  follow its `/__namespace/` convention and slot into the existing pathname
  dispatch. `src/lib/devWrite.ts` is the DEV-gated client for it.

## Commands

| | |
|---|---|
| `npm run dev` | Vite dev server — the only mode with editing |
| `npm test` | vitest (`vitest run`) — the suite must stay green |
| `npm run typecheck` | `tsc -b --noEmit` |
| `npm run build` | `tsc -b && vite build` → `dist/` |
| `npm run build:snapshot` | regenerate a snapshot from sources |

Tests are co-located (`*.test.ts`/`*.test.tsx`) beside what they cover. Several
read files off disk to assert CSS/config facts — when you change a token or a
rule, expect a disk-reading test to care.

## Binding decisions (`docs/adr/`)

- **ADR-001** static-first React + Vite + Primer
- **ADR-002** config / readings / snapshots data model
- **ADR-003** pluggable ingestion scaffold; dev-only local write path
- **ADR-004** auto-deploy to GitHub Pages on push to `main` (`.github/workflows/deploy.yml`
  runs `npm ci` → `npm run build` → publishes `dist`)

Read the relevant ADR before changing anything it covers; if a change contradicts
one, that is a decision to raise, not to make silently.

## Conventions

- **Accessibility is not optional.** Status is conveyed by **shape *and* colour**
  (colourblind-safe), never colour alone. Contrast is checked by disk-reading
  tests in `src/styles.*.test.ts`.
- Both **dark and light** modes must work; tokens live in `src/styles.css` and
  are mode-aware. Dark is the default.
- Per-bucket accent colours come from `src/lib/accents.ts` via the `--c` custom
  property — one source of truth, used by every bucket surface.
- Prefer extending an existing token/class/module over adding a parallel one. If
  you find yourself creating a second thing that does what an existing thing
  does, stop — that is the failure mode this repo keeps hitting.

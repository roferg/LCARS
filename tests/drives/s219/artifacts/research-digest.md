# Research — what the 16 research agents were asked, and what each recommended (digest)

## Q1
**Asked:** In the DX-Scorecard MBR builder, per-KPI "delta vs last MBR" is defined as this month's value minus the same KPI's value in the previous published MBR, but KPI values are free-text MetricValue strings (e.g. "5.46 days", "18", "<= 1 day", "42%") or cohort SubReading[]; what algorithm parses these strings into comparable numbers, how are units/suffixes/inequalities handled, and how is the delta rendered when a value is non-numeric or unparseable?

**Recommended:** Add a single pure helper (e.g. `parseMetricValue(raw): { n: number, unit: string } | null`) that: (1) strips leading inequality/qualifier tokens (`<=`, `>=`, `<`, `>`, `~`, `approx`), (2) matches the FIRST signed decimal number via regex `-?\d[\d,]*(?:\.\d+)?` (removing thousands commas), and (3) captures the trailing unit/suffix by normalizing the remainder (`%`, `days`/`day`, `s`, `/day`, etc.). Compute the delta ONLY when both the current and previous readings parse to a number AND share the same normalized unit; otherwise treat it as incomparable. For cohort `SubReading[]`, parse and diff per matching `label`, never across the whole array. Render an incomparable/unparseable/unit-mismatched delta as a neutral em-dash placeholder (`—`) with no arrow or sign, so free-text values like `WIP`, `Monitor`, or `<= 1 day` never produce a misleading numeric delta.

## Q2
**Asked:** In the DX-Scorecard MBR data model (shared/types.ts Kpi/Snapshot), there is currently no field to persist the computed delta-vs-last-MBR, per-cohort-source deltas, the "Carried" provenance flag, the previous-MBR value ("was {old}"), or the draft's "last edited" timestamp; which new persisted fields should be added to Kpi/Snapshot to back these, given the draft persists to data/snapshots/<id>.json and is later rendered read-only?

**Recommended:** Add four optional per-KPI fields to `Kpi` and one optional snapshot-level field to `Snapshot`. On `Kpi`: (1) `previousValue?: MetricValue` — the last-MBR value, backing the "was {old}" display and the scalar delta; (2) `delta?: string` — the persisted, pre-computed overall delta-vs-last-MBR display string (e.g. "-0.42 days"); (3) `sourceDeltas?: SubReading[]` — per-cohort-source deltas, reusing the existing `{ label, value }` shape aligned to the cohort breakdown; (4) `carried?: boolean` — an explicit provenance flag replacing the in-memory `carried` Set so "carried over" survives read-only rendering. On `Snapshot`: `lastEditedAt?: string` — an ISO timestamp stamped by the draft's `saveSnapshot`/`editKpi` path. Keep all fields optional so older locked snapshots and freshly seeded drafts remain valid, and let the build/reconcile step compute and stamp them at seed/refresh time rather than deriving them at render.

## Q3
**Asked:** In the DX-Scorecard MBR builder, which KPIs count as "automated/wired" (collectable, "Auto" tag, Collect controls) versus "manual" (inline-editable, "Manual" tag) — is it derived from a non-empty aiUpdateInstructions, from the hardcoded WIRED_METRIC_IDS list in src/views/MbrBuilderView.tsx, or another signal — and how is the "11 of 14 automated" count computed?

**Recommended:** The Auto/Manual partition that drives the "Auto"/"Manual" tags, Collect controls, and the "N of M automated" count is derived from a non-empty aiUpdateInstructions (a trim-strict predicate), NOT from the hardcoded WIRED_METRIC_IDS list. The instructions are resolved from the roster (config.json) as the sole authority per ADR-002; WIRED_METRIC_IDS is a separate, narrower MBR-builder refresh-wiring signal and should not be used for the automated/manual count.

## Q4
**Asked:** In the DX-Scorecard MBR "Pull data & start" collection screen (per-bucket Queued to Collecting to "N values pulled" behind a progress bar), does collection invoke the real per-KPI CLI endpoint POST /__collect/<kpiId> (up to ~240s each), the stub POST /__mbr/refresh pipeline, or both, and how is the mockup's "~30s" hint and per-bucket progress reconciled with real per-KPI collection latency?

**Recommended:** Drive the MBR 'Pull data & start' screen off the REAL per-KPI endpoint POST /__collect/<kpiId> (the shelled-out Copilot CLI, one KPI at a time), NOT the stub POST /__mbr/refresh, and model per-bucket progress as an aggregation over those sequential per-KPI runs. Because a real collect is minutes, not seconds, drop the mockup's misleading '~30s' hint: show per-KPI Queued→Collecting→done substeps (each bounded by the 240s CLI timeout), let the bar advance as each KPI completes, and surface an honest estimate (~2–4 min per KPI, roughly M×2.5min total) rather than a single 30s promise.

## Q5
**Asked:** In the DX-Scorecard MBR Reviews entry screen, how is the "Next up · {Month Year}" (next unstarted month) determined from existing snapshots, and what id does a newly-started draft receive — a month-keyed YYYY-MM, the date-keyed YYYY-MM-DD.N scheme used elsewhere, or something else — given the reviews and Published lists are organized by month?

**Recommended:** Derive "Next up · {Month Year}" purely as a display label — group snapshots by their human `month` field (or the YYYY-MM prefix of each id), find the calendar month after the newest existing review, and show that month with no snapshot yet as the next-up card. But when a draft is actually started, mint its id with the canonical date-keyed `YYYY-MM-DD.N` scheme via `nextDraftId(existingIds, today)` (ADR-003), NOT a month-keyed `YYYY-MM`. Keep the human `month` string (e.g. "August 2026") on the snapshot to drive the by-month grouping of the Reviews/Published lists; the id and the month label are separate concerns.

## Q6
**Asked:** In the DX-Scorecard MBR builder, when there is no previous published MBR (the first-ever MBR, or a KPI absent from the last published MBR), how should the "vs last MBR" delta and the per-source "change vs last MBR" column be computed and rendered (e.g. blank, "new", "no change", "—")?

**Recommended:** When no prior published MBR baseline exists for a value (first-ever MBR, or a KPI/source absent from the last published MBR), do NOT compute a numeric delta and do NOT render "no change" or "0". Render an inert em-dash placeholder "—" (the repo's established 'not-applicable' glyph) as the neutral default, and additionally surface a subtle "new" badge only for a KPI/source that is genuinely new relative to an existing prior snapshot. Reserve "no change" strictly for the case where a prior baseline DID exist and the value is unchanged — never for a missing baseline.

## Q7
**Asked:** In the DX-Scorecard MBR lock flow, the redesigned lock dialog drops the "Locked by" handle field and unlock drops the amendment note, yet Preview/View reuse src/views/LockedView.tsx which renders a "Locked by {handle}" provenance line and an Amendments audit section; what value should Snapshot.lockedBy now hold, and should the "Locked by" line and the amendments audit trail be removed, hidden, or retained?

**Recommended:** Set Snapshot.lockedBy to null on newly locked snapshots (keep the existing `string | null` type), and do NOT delete the LockedView rendering — instead make the "Locked by" provenance line conditionally HIDDEN when lockedBy is null, and RETAIN the Amendments section unchanged (it already renders nothing when the array is absent/empty). This drops the dead fields from the redesigned flow while still faithfully rendering already-locked historical snapshots that carry a handle and/or amendments.

## Q8
**Asked:** In the DX-Scorecard MBR redesign, which new surfaces (Reviews entry screen, collection screen, builder, Preview) are gated behind import.meta.env.DEV like today's MbrBuilderView, and which — e.g. viewing a published month via the existing #locked/<id> LockedView path invoked by the "View" button — remain available in the read-only production build?

**Recommended:** Gate every authoring/editing surface of the redesign — the Reviews entry screen, the collection screen, the builder, and the pre-publish Preview — behind import.meta.env.DEV exactly as MbrBuilderView and EditRosterView are today, so Rollup dead-code-eliminates them and the build-purity test stays green. Keep only the read-only published-month view served by the existing #locked/<id> LockedView route (the destination of the "View" button) in the production bundle; it ships because it renders committed, immutable snapshot JSON with no write path.

## Q9
**Asked:** In the DX-Scorecard MBR multi-screen redesign (Reviews entry then collection then builder then Preview), what hash-route structure should be used given App.tsx/useHashRoute currently expose only a single #mbr route, and how do the Continue-to-builder, Cancel, Discard, Preview, and back-out transitions map onto those routes?

**Recommended:** Keep a single 'mbr' RouteView but namespace the four screens as segmented sub-routes under the #mbr prefix, parsed exactly like the existing #locked/<id> pattern: #mbr (Reviews entry/list) → #mbr/collect (collection) → #mbr/build (builder) → #mbr/preview (Preview). Extend parseHash so head 'mbr' reads rest[0] into a new `step` field (defaulting to the Reviews entry when absent), and have App keep dispatching the whole family to the DEV-gated MbrBuilderView, which switches on route.step. Map the transitions as: Continue-to-builder navigates #mbr/collect → #mbr/build; Preview navigates #mbr/build → #mbr/preview; back-out from Preview returns #mbr/preview → #mbr/build; Cancel (from collection) returns to the Reviews entry #mbr; and Discard (from builder, after its confirm modal) also returns to the Reviews entry #mbr.

## Q10
**Asked:** In the DX-Scorecard MBR builder, insights autosave "debounced while typing" before a PUT /__data/snapshots/<id> write — what debounce interval should be used, and how should the "Last edited {t}" meta be formatted (relative like "2 min ago" or absolute timestamp)?

**Recommended:** Debounce the autosave at 800ms of typing-inactivity (a value in the 500–1000ms band; 800ms is the sweet spot), and render "Last edited {t}" as an absolute, locale-aware timestamp (e.g. "Jul 27, 2026, 3:04 PM") produced via the existing UTC-pinned date helper — not a live relative "2 min ago" string.

## Q11
**Asked:** In the DX-Scorecard MBR builder, editing a manual KPI's value recomputes its delta-vs-last-MBR automatically; for a cohort (SubReading[]) manual KPI, how is per-sub-source inline editing handled, and how is each source's "change vs last MBR" recomputed and matched to the previous published MBR's sub-readings (by label, by order)?

**Recommended:** The premise does not hold in the current codebase: there is NO automatic 'delta-vs-last-MBR' recomputation for any manual KPI (scalar OR cohort), so nothing matches sub-readings against the previous published MBR today. Per-sub-source cohort editing exists only as plain {label,value} row editing in UpdateKpisView's ManualValueEditor (which just emits an updated SubReading[]); MbrBuilderView's editKpi only patches the value and persists the draft, computing no diff. If a per-source 'change vs last MBR' is desired, it must be BUILT, and it should match sub-readings by their `label` (the only stable identifier) with positional order as a fallback tie-breaker, since SubReading carries no id.

## Q12
**Asked:** In the DX-Scorecard MBR builder, does the "Refresh-all" / re-pull action (automated KPIs only) run inline within the builder with per-row Collecting/✓ chips, or route back through the standalone collection screen, and should its indeterminate progress strip plus "11 of 14" warning live inside the amber warning box exactly as the mockup shows?

**Recommended:** Route the automated (auto-only) re-pull through the standalone collection screen (UpdateKpisView), which already owns the per-row Collecting/✓ state chips and the indeterminate progress strip; do NOT build a second chip pipeline inside the MBR builder. And do NOT nest the progress strip inside the amber warning box — keep the "11 of 14" (N-of-M) automation warning in its own amber warn-line and render the indeterminate strip as a separate sibling below the action bar, exactly as the mockup lays them out.

## Q13
**Asked:** In the DX-Scorecard MBR builder, confirm the mapping of the five status-select labels "On track / Watch / Off track / Tracking / WIP" to the existing MetricStatus enum (positive/warning/negative/neutral/wip) and that the off-track marker uses an X shape (via src/lib/status) distinct from the on-track filled circle without relying on colour.

**Recommended:** The label-to-enum mapping is confirmed and correct (positive=On track, warning=Watch, negative=Off track, neutral=Tracking, wip=WIP), but the off-track marker does NOT use an X shape — it is currently a solid diamond. If an X is required, change STATUS_META.negative.shape to 'x' in src/lib/status.ts, add a matching .status-dot--x rule in styles.css, and update the shape tests; otherwise keep the existing diamond, which already provides a colour-independent silhouette distinct from the on-track filled circle.

## Q14
**Asked:** In the DX-Scorecard MBR builder, a KPI is "Carried" when the data pull returns no fresh value and value/status are carried from the previous published MBR; how is "no fresh value" detected at pull time for a wired KPI (collection failure, empty result, or unchanged value), and is the Carried flag cleared once the user manually edits that KPI's value?

**Recommended:** "No fresh value" is detected purely by the ABSENCE of a source reading for that KPI id in the current pull (buildSnapshot's `if (!fromSource) return kpi;`): both a collection failure (the source throws and is swallowed in runSources, contributing zero readings) and an empty result (the source emits no reading for that id) collapse to the same missing map entry, so the KPI carries value/status/insight forward. "Unchanged value" is NOT a carry trigger — if a source emits any reading, even one identical to the prior value, it is applied as fresh and clears the badge. And the Carried flag is NOT cleared by a manual value edit: the client's `editKpi` never touches the `carried` set, so only a refresh (refreshOne/refreshAll/seedFresh) clears the "carried over" badge — this is a latent bug where a manually-overwritten carried KPI keeps showing the badge.

## Q15
**Asked:** In the DX-Scorecard MBR builder, "target comes from the KPI's config/default view" — should the builder read target from live config.json (via overlayRoster) at pull time and freeze it into the draft snapshot or continuously mirror live config, and for manual KPIs how does the "From default view · edit to override" seeding pull the latest value from the default scorecard tab?

**Recommended:** Do both, along the seam the codebase already defines: FREEZE the target into the draft snapshot at pull/seed time (reconcileRoster/buildSnapshot copy `config.target` into the on-disk snapshot JSON so a locked MBR is self-contained and immutable), while the live Default view keeps MIRRORING config.json read-only via the pure `overlayRoster` (which re-projects `name`/`target`/`drilldown`/`aiUpdateInstructions` at render without mutating disk). A draft's target is therefore snapshotted at the moment you pull, not continuously mirrored into the persisted draft. For manual KPIs, the "From default view · edit to override" seed should pull the latest committed value by carrying it forward from the most-recent (default/latest-locked) snapshot matched by KPI id — the value reconcileRoster/manualSeedValue already seeds — which is itself config/target-overlaid when the Default tab renders; that seeded value stays editable so the analyst can override it before locking.

## Q16
**Asked:** In the DX-Scorecard MBR Reviews entry screen, if a draft for the next month already exists on disk (in-progress, not yet locked), should its start card still show "Pull data & start" (re-pulling/reseeding) or a "Continue draft" affordance, and does re-pulling an in-progress draft preserve existing insights and manual values per the re-pull-preservation rule?

**Recommended:** When an in-progress (unlocked) draft already exists on disk, the start card should present a "Continue draft" affordance that resumes the existing draft in place — NOT a "Pull data & start" reseed. Re-pulling should never be the default entry action for an existing draft; a fresh reseed must be a separate, explicitly confirmed 'discard' action. And yes: a re-pull performed on an in-progress draft preserves existing human insights and manual (unwired) values per the re-pull-preservation rule — only wired KPIs get fresh source values, everything else carries forward. A full reseed/discard is the one path that overwrites them.

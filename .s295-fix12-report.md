# S295 fix 12: stopped at the honesty gate

**No liveness line implemented.** The existing round interface supplies no
continuously fresh evidence of remote progress during a silent API wait.
Printing elapsed time periodically from that interface would not satisfy the
requested proof-of-progress contract. This takes the explicit "challenge me"
stop path; it does not claim to fix the silence.

## What the code actually exposes

- `skills/lcars-xo/xo.sh:5407-5411` prints the round's "looking" message.
  At lines 5483-5489 it starts `spawn-number-one`, redirects that invocation's
  stdout and stderr away from the terminal, and waits for it to finish.
  Notes and the verdict are collected after that wait. There is no periodic
  terminal progress line in this wait.
- `skills/lcars-run/worker-adapter.sh:345` selects Claude's text output.
  Its Copilot invocation uses `-s` (lines 351-376). Lines 492-497 capture the
  worker's stdout and stderr in `.worker.out` and `.worker.err`, then record
  `.worker.rc` after the invocation returns. These are not a transport-level
  progress acknowledgement or a guaranteed periodic event stream.
- There IS existing best-effort telemetry:
  `skills/lcars-run/run.sh:21410-21431,21515-21589` maintains
  `worker-liveness.json` when the hang guard is enabled and a Mission directory
  is available. It derives `producing` from output-file size/mtime changes,
  `thinking` from local process-group CPU, and otherwise `quiet`. Writes are
  state-change-driven, not periodic terminal messages. The disabled guard
  returns before this telemetry is established (lines 21489-21498).
  This is not evidence that the reported 48-minute wait was hung.

## Why the available candidates are insufficient

1. Elapsed time plus a live PID proves that a local process still exists, not
   that its pending request is progressing. A blocked process can satisfy both
   indefinitely; a surviving wrapper can also outlive its worker.
2. CPU changes are not an acknowledgement from the remote reviewer. The
   measured healthy wait was almost locally idle, and local bookkeeping could
   consume CPU without advancing the review.
3. Fresh output, screenshots, or completed controls could support an honest
   **event-driven** progress message. But none is guaranteed during the silent
   reply wait that triggered this request. Printing only on those events would
   leave that exact silence unresolved; replaying their last counts every
   minute would imply freshness that has not been observed.

This is a limit of the current observable contract, not a claim that progress
telemetry is impossible in principle. A verified source of fresh worker or
request progress would be needed before promising periodic proof of progress.
A line explicitly saying "local process present; remote progress unknown"
would be honest uncertainty, but is not the requested proof of life.
